# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**QUAM State Manager** is a desktop + web tool for inspecting and editing quantum machine (QUAM) state files. It reads `state.json` + `wiring.json`, resolves custom JSON pointer references, and provides a CLI, Flask web UI, and pywebview desktop app. It also generates fresh QUAM configurations (Generate Config wizard) and previews `machine.generate_config()` output (Config Viewer).

## Architecture

### Core Pipeline

```
state.json + wiring.json
    → safe_io.read_state_wiring (FILE_SHARE_DELETE + mtime-bracketed pair read)
        → loader.py (QuamStore — owns per-instance pointer cache)
            → pointer_resolver.py (resolves #/, #../, #./ references via store cache)
            → search_index.py (prefix map + trigram index)
            → query.py (flattens nested JSON → qubit/pair dicts)
            → modifier.py (type-coerced edits, undo, rollback)
            → saver.py (atomic writes via safe_io.atomic_write_json, .bak rotation)
            → differ.py (2-way diffs, N-way trends)
            → history.py (Param History: SQLite property index, snapshots)
            → config_view.py (Config Viewer — preview generate_config())
            → config_generator.py (Generate wizard subprocess driver)
```

### QUAM Pointer System

QUAM files avoid value duplication via three pointer types:
- `#/qubits/qA1/f_01` — absolute from root
- `#../x180/length` — relative to parent
- `#./self_ref` — relative to self

`pointer_resolver.py` resolves these **on-read, never in-place**. The cache is **per-`QuamStore`** (each store owns its own dict + lock), so two chips loaded in the same process with same-named qubits never share resolutions. Unresolvable pointers return raw strings + log warnings (real data has dangling pointers). See `docs/32_red_team_phase_2.md` finding 0.1 for the chip-isolation bug this fixes.

### QuamStore (Thread-Safe)

`core/loader.py` holds merged state+wiring dicts, change log, search index, and per-store pointer cache in a single `QuamStore`. All mutations are guarded by `threading.RLock` (Flask workers + pywebview UI thread share state). Loads route through `safe_io.read_state_wiring` so the read never blocks an experiment's atomic save on Windows.

### Working-Copy / Live-File Safety

Experiment programs read and write the same `state.json` + `wiring.json` the app watches; on Windows a plain `open()` for read blocks their atomic `os.replace` save. So the app operates on a **working copy** under `instance/working_state/` (`core/working_copy.py`): the `QuamStore` and `Saver` are built on the copy, background change detection is `os.stat`-only, and the live files are read only on an explicit user **sync** and written only on an explicit **apply to live**. All live-file content I/O — across `loader.py`, `scanner.py`, `history.py`, `working_copy.py`, and the Saver — goes through `core/safe_io.py` (share-delete reads, `ReplaceFileW` writes, transient retry, mtime-bracketed pair read). LRU eviction in `_activate_quam` keeps the on-disk working folder so a re-load rehydrates the user's unapplied edits via `working_copy.load`. See `docs/28_conflict_safe_io.md`.

**State-roundtrip invariant (docs/65):** content loaded WHOLESALE into the working copy (dataset **Load State**, State-History stage, **Revert last apply**) has no change-log entries and a cleared re-apply stash — `/state/sync` must never pull-first over it. `mode=apply` with `working_dirty and not pending_reapply` delegates straight to the save+push path; `discard`/`reapply` answer `needs_confirm` until `force=1` (client turns it into one confirm). The stash carve-out keeps conflict resolution (pull+replay) working — `/save` stashes, so saved edits keep the merge model; a `ctx["staged_base"]` marker (set by stage routes, cleared on apply-success/pull) overrides the carve-out so staged+edited mixed state still pushes whole (audit-r10). Revert-last-apply's fallback target is CONTENT-MATCHED (`snapshot_ts_for_current_content`), never `_snaps[0]`. Staleness conflicts on staged content render the honest tray variant (`staged_conflict` — overwrite-live or pull-and-discard only). Client bridge: `stateRestored` soft-refreshes the state surface (the grids listen only to `quam:state-changed`, which HX-Trigger can't emit) and keeps a dataset-detail inspector open. Pinned by `tests/test_state_roundtrip.py` + `tests/state_sync_selfcheck.cjs`.

**SM never swaps what you are looking at (docs/87).** `reconcile_with_live` used to auto-pull whenever the working copy was **provably clean** — which describes exactly the person most likely to be hurt by a mis-run: someone who edited nothing in SM, so SM held the good state. It was replaced without a question. The stale-chip bug the auto-pull was built for was the SILENCE, not the absence of automation, so the user-facing path now passes `sync_if_clean=False` and the docs/86 banner asks (its tests are correspondingly STRONGER: kept + banner + one click reaches the new chip). The identity gate (C30) already refused to auto-pull a hardware-different chip, so the silent path only ever covered same-chip-different-values — the qualibrate fit-update AND the mis-run, mechanically indistinguishable. **`auto_adopt` splits ACTORS, not behaviours**: `_reconcile_cached_quam_ctx`'s three callers are the user opening a chip (`False`) versus the scheduler's post-node hook and the autofit engine's `reconcile()` (`True`) — autofit's gates judge each fit against the **pre-update anchor** (docs/47), so a stale store makes the VERDICT wrong; a robot mid-loop does not stop to ask. Consequence, confirmed with the user: a run started from SM's own Experiment Runner still adopts silently (the machine hook fires before the next render); only writes from OUTSIDE SM raise the banner. The banner stopped being vague — `reconcile_with_live` gained an optional `out` dict handing back the two documents it ALREADY read to reach its verdict, so `_drift_count` diffs them for free and the banner says "N values differ" with zero added live reads on a surface that renders on every page (None ⇒ say nothing, never invent). Removed with the silence it announced: `/state/drift`'s `_auto_pulled` one-shot and its "✓ Live chip updated" toast — a toast reporting a fait accompli is worse than a banner that asks first. Side effect: FOUR entries left the Windows environmental-failure baseline (`TestRestartCleanCopy::test_legacy_meta_replaced…` + `TestBannerSlot` ×3 asserted the banner appears and the auto-adopt raced them), so the baseline is **14**, not 18. Pinned by `tests/test_live_replace_routes.py` + `tests/test_sync_robustness.py`, with `tests/test_autofit_e2e.py` unchanged as proof the carve-out is real.

**A field the entity has not got yet (docs/88).** Typing into `lo_mode` in Live State Edit answered `Parent at 'qubits.qC4.resonator.opx_input.lo_mode' is str, not dict or list` for EVERY value — both spellings failing was the tell that it was never about the value. `qubits.<q>.resonator.opx_input` is a POINTER to a port dict that does not carry `lo_mode` while its siblings do (which is why the grid derives the column at all), so `resolve_field_target` dead-ended, `resolve_edit_path` fell back to the RAW path, and the modifier tried to walk into the pointer STRING. Two halves: `edit_policy.resolve_missing_leaf_path` returns `<resolved parent>.<leaf>` when only the final key is absent (a list parent returns None — appending is not "filling in a field" and must never be inferred from a cell edit), so the resolver can never again hand the modifier a pointer-parent path; and **creation stays DECLARED, never inferred** — the first attempt created any absent leaf and `test_accept_added_leaf_without_flag_fails` caught it, whose invariant ("a generic bulk/plot edit can't silently create a mistyped path") is worth more than the convenience. So the existing per-update `create` flag is the gate and the grids declare the one case they know: the server marks a cell it rendered "not set" with `data-missing`, the grids turn that into `create: true`. The batch's pre-existing create fallback also had to create at the RESOLVED target rather than the posted alias — creating at the pointer path could only ever fail, so the flag alone would not have rescued this. Creating stays type-safe for free (`create_subtree` runs the same `check_subtree`, so an env-schema-unknown field is still refused — an invented key is a `Quam.load()` crash). Pinned by `tests/test_missing_leaf_edit.py`.

**The third choice when live drifted (docs/86).** When something outside SM rewrites the live files, the drift banner offered *Review & sync · Pull live state* and the review modal's **clean** branch offered *Sync* — one direction, not a choice. The case behind the reports is a test run that wrote parameters by mistake, where the state SM is holding is the good one. "Write my working state over live" was already implemented and already exposed in the modal's `working_dirty` branch and in the staleness conflict tray (`Overwrite live (force)`) — it was missing exactly where the user has made no edits of their own, and `/state-history/<ts>/restore-live` could always do it anyway; what was missing was reaching it at the moment the user is TOLD about the drift. So `↑ Keep mine — overwrite live` now sits last and un-primary in both surfaces (same error-tinted style as the conflict tray's force button — one visual language for one act), gated `not archive`. Pull and push are NOT symmetric — a pull discards the working copy while the live files stay on disk, a push discards live content that may be a real calibration — so: **it is reversible and says so** (`/state/apply-to-live` already snapshots the pre-apply live into `ctx["last_apply"]`, which arms the tray's *Revert last apply*; that property is why this is offerable at all), **one confirm that names what disappears** via `GET /state/overwrite-live/preflight` (live-diff count, unsaved-edit count, run-in-progress, reversibility) — a separate endpoint fired ON CLICK, never a count baked into a banner that renders on every page (docs/28 forbids live reads on render) — and **the push is forced**, because the chip has drifted by definition and an unforced push would land on the conflict screen and ask twice. A run in progress is REPORTED not blocked (there is no scheduler edit-lock on the write path; a run going wrong is the reason the user is here), an unreadable live folder yields an honest "unknown" count rather than a refusal, and archives 409. Verified on a real 21-qubit chip: 42 out-of-band values → clean branch shows Sync + Keep-mine → preflight says 42 → overwrite restores all 42 in 810 ms → staging `last_apply.pre_ts` brings the run's values back. NOT changed: a provably-clean working copy still auto-pulls (`RECONCILE_SYNCED`) without prompting — the stale-chip fix — so that half of the report wants a revert affordance after adoption, not a blocked adoption. Pinned by `tests/test_overwrite_live.py` + `tests/state_sync_selfcheck.cjs`. **One directional-trio vocabulary (docs/97):** the same three actions were labeled SIX ways across the surfaces (`Discard`/`Sync`/`Pull live state`/`Discard & pull live`/`Pull latest & discard mine`/`Pull & discard`), so the pull-and-discard never read as the symmetric opposite of Keep-mine and users thought it was missing. Every surface (banner, `_state_review.html` all three branches, `_state_apply_conflict.html` both branches) now uses **↓ Take live** (`mode=discard`, working←live) · **↑ Keep mine — overwrite live** (`apply-to-live?force=1`, working→live) · **⇄ Pull & apply (merge)** (`mode=apply`) + secondary *Re-apply (review first)* — handlers/routes/modes UNCHANGED, label + scoped-CSS only. The review popup's per-field Δ was the least-visible element (~10px, unstyled `.review-delta`); now a prominent chip (new `.state-review .review-delta` + enlarged value line, all `.state-review`-scoped; `.sync-btn-sub` qualifier never touches the global `.btn-sync`/`.btn-sm`). Label pins updated in `tests/test_review_scroll.py` + `test_overwrite_live.py` + `test_state_roundtrip.py`; `state_sync_selfcheck.cjs` unchanged (pins modes, not labels).

The **load path is content-hash-aware** (fixes the stale-chip bug — replacing a live folder's files out-of-band used to keep showing the old chip even across restarts): each sync point records `synced_live_hash` (sha256 of parsed state+wiring) in the meta sidecar, and `reconcile_with_live` runs on load/select (never in background polls) — live replaced + working copy provably clean ⇒ auto-pull; replaced + (possibly) edited ⇒ keep + `live_diverged` banner (never clobber, all sync/save/apply mutators serialize on the per-folder build RLock); unreadable live ⇒ never treated as replaced. Working-copy **GC** (`/api/working-copies/scan|gc` + threshold banner) deletes only provably-clean copies — transient read failures classify as kept-unverifiable, never deletable; the in-use set folds in every LIVE peer window's open chip via `instances.peers()` + `working_copy.key_for` (liveness alone protects — a peer's in-memory edits scan clean on disk; dead/corrupt registry entries protect nothing and never block GC).

### Scanner + LRU Cache + Sidebar Tree v2

`core/scanner.py` discovers experiment folders lazily. `QuamStore` instances are LRU-cached (max 10, ~40MB total) — only loaded when selected in the UI. `node.json` reads also go through `safe_io.read_json` so workspace navigation can't break a still-active experiment's write.

**Sidebar tree v2 (r13, docs/68):** `Workspace.tree` stays the flat `{root: [DateGroup]}` data model; `build_nested_tree(root, entries)` derives the VS-Code-style render model per root (real folder levels — `root/<chip>/<date>/#N` exposes the chip; date-like levels DESCENDING, today on top; leaf entries run-id DESCENDING with the 50-cap keeping the **newest** 50 — the old oldest-50 slice was THE "sidebar sometimes doesn't refresh" bug on >50-run days). Row markup lives in the `entry_rows` macro (`_sidebar_tree_macros.html`, shared with the `tpath`-addressed "Show all" fragment — include-in-macro can't see macro-locals). Staleness = **structure-spine probe**: per root, the recorded set of run-parent dirs + ancestors is re-statted as a `{dir → mtime}` map (detects additions at any depth; immune to one future-dated sibling pinning a max; `DatasetStore._current_mtime` carries a `(max_mtime, n_date_dirs)` tuple for the same reason). `rescan_root` scans OUTSIDE the lock and swaps the tree in one rebind (readers never see the root missing). The tree poller advances `lastV` only after a successful swap, has a 10 s abort + `visibilitychange` catch-up; `/datasets/changes-since` returns the MIN of per-folder cursors and a failed folder rescan holds its cursor at `ts`. The active run's ancestor `<details>` get `.tree-branch-active` (`_markActiveTreeBranch`) so a collapsed tree still shows where the open experiment lives; `dsNavRun` ↑/↓ = newer/older (spatial order).

**Δ everywhere (docs/76).** Every before→after surface renders old, new AND the difference through ONE implementation: `core/value_delta.py` (+ the `value_delta` Jinja filter and `_delta_macros.html`'s `delta_chip`/`delta_cell`/`delta_block`) server-side, `window.ValueDelta` (app.js) client-side — the two are pinned character-for-character by `tests/test_value_delta.py` because the same screen renders both. The subtraction is **exact decimal** (float would print 5.2−5.1 as 0.10000000000000053) and the formatting matches the `group_digits` values beside it (`+100,000,000 (+1.96%)`, exponential only past 1e15 / below 1e-6). A Δ renders ONLY when it means something — booleans, nulls, pointers, strings and created/deleted subtrees render nothing, never a fabricated 0; a numeric string still diffs but the tooltip says it was stored as text (docs/56 r14). Wired: Review tray, the live-vs-working **sync** screen (recomputed as the user edits the live value), the plot-click/fit-apply popup (recomputed on edit) + ndview Stage, both Live-Edit grid hover chips, the FSP compensation table, Prev-State diff, Compare-selected (fit + params), value/Column History, the autofit ledger + diagnose confirm, `/changes`, the inspector "Modified — was:" tooltips and the undo toast. The six older diff/compare macros were UNIFIED onto it (they used to print `%+.3e` where the tray prints grouped digits).

The qubit and pair inspector panes (`/qubit/<name>`, `/pair/<name>`) carry a **sticky in-panel search bar** in `_inspector_header.html` (gated by `inspector_type in ('qubit','pair')`). The JS `filterDetailPanel` in `app.js` filters `<tr>` rows across all `<details>` sections by AND-tokens, includes section names + editable `<input>.value` in the haystack, auto-opens matching sections, hides empty ones, and shows "X of Y" — same UX as `/compare`'s diff filter but spans multiple tables.

**The diff workbench is the front door (docs/84).** The hub is correct and nobody used it: three "Compare selected" buttons led to three different surfaces, and the one users reached asked for a declared context + a tolerance preset + sometimes an entity mapping BEFORE showing a row. `/diff?a=<ref>&b=<ref>&tab=state|wiring|node|data&view=tree|list` shows the differences and how big they are, IDE-style. The tree is the Explorer's own `renderJsonTree` (search, depth, lazy children) — which already had a diff overlay (live diff uses it) but ① iterated the PRIMARY document's keys, so a key only one side had rendered as NOTHING, and ② printed its own `toFixed(6)` delta, so one change read `(+0.000123)` here and `+100,000,000 (+1.96%)` in the tray. Now: `options.union` (opt-in — live diff is byte-identical, pinned) makes added/removed first-class incl. removed subtrees that still expand, and the delta goes through `ValueDelta` (docs/76). **"Differences only" is a PRUNED document, not a filter**: `core/json_diff.py` flattens both sides, ranks rows by |Δ%| (numeric moves first — a real first-vs-last pair has 2,758 differences of which only 117 are numeric, the rest regenerate churn), and prunes each side to changed leaves + ancestors — neighbouring snapshots prune to **4 nodes of 15,285 (0.5 KB)**, whole build 20–45 ms. Primary = BEFORE, `refData` = AFTER in both modes so rows read A→B. Sources are the hub's own ref tokens via `compare_sources.resolve_source`; a bare `/diff` opens newest-snapshot-vs-loaded-chip (no picking); the list pages at 300 rows (2,257 ranked rows = 1.2 MB). `data` is a variable INVENTORY diff (files/vars/dims/shapes) — a byte diff of HDF5 arrays is not meaningful and pretending otherwise would be dishonest. One front door: `/diff/snapshots` (both history pages, oldest side left) + `/diff/runs` (Datasets, exactly 2 → node tab) resolve identity server-side; the sidebar's Compare opens `/diff`; the hub sits behind "Advanced…" keeping entity mapping + N-way baskets, and every legacy URL still redirects into it. Verified on two real runs: the node tab names what was ASKED differently (`artificial_detuning_in_mhz`, `num_shots`, `amp_max/min`). Pinned by `tests/test_diff_workbench.py` + `tests/diff_tree_selfcheck.cjs`.

**One search grammar (docs/96).** space = AND, a standalone `|` = OR (tight binding: `x180 amplitude | length` = x180 AND (amplitude|length)), every other pipe literal (`|e>` ket text stays searchable). `web/static/search-query.js` + `core/search_query.py` are JS<->PY parity-pinned; wired into both tree-search paths, the bulk/pair grids, the Datasets table and the sidebar filter. Scoped surfaces keep their own tokenizers and compose at the group level — negated terms never join an OR group. **A token that NAMES a row wins the row axis (docs/110, 2026-08-11).** Both grids classify each token as column/id/value, and each axis reads a both-hit token as NEUTRAL — so a token hitting a column AND a qubit id filtered NOTHING AT ALL, on either axis. That is the normal case, not a corner: a chip's pair-gate columns carry the partner qubit's name in their `search` text (`cz_SNZ_flux_pulse_qA1`, folded headers/docs/85), so on a real 21-qubit chip EVERY qubit id was dead as a search term — including the placeholder's own promise. Classification is now exclusive by precedence and a token that is a PREFIX of some row id takes the row reading (the grid is one row per qubit; reading `qA1` as a column filter would show three pair columns across all 21 rows). A token merely occurring INSIDE an id keeps the column reading, so column search is unchanged. Same classifier, same fix in the pair grid. **Every numeric parameter, as change points (docs/83).** The curated eleven (`DEFAULT_TRACKED_PROPERTIES`) were the only trended fields; anything else fell to `field_history`'s capped scan — measured on a real 264-snapshot chip, **555 ms and truncated at 150 snapshots** vs 2.6 ms complete for T1. Indexing every leaf densely is impossible (8,000 leaves × 111 snapshots = 887k rows ≈ 200 MB/chip at the ~235 B/row the existing index really costs); indexing only the TRANSITIONS is, because between consecutive snapshots of a real chip the number of numeric leaves that CHANGE has a **median of 2–4 out of 8,000**. `core/leaf_index.py` (`leaf_snaps`/`leaf_paths`/`leaf_cp` inside the chip's existing `index.sqlite`, own version marker in `leaf_meta` so it can never trigger the `param_history` pair-row upgrade) ends up **smaller than the eleven-property index beside it** (2.02 MB vs 6.1 MB on LabA; 1.09 vs 26.9 on ExampleChip_1Q) with one path's full history at **0.01–0.06 ms**. Ingest is nearly free — the snapshot's `state.json` is already parsed for the curated rows, so the walk is +7–39% on a parse we already do. **Pointers are FOLLOWED** (1,000–2,300 pointer leaves/snapshot, 570–1,190 resolving to numbers — as many parameters again as the direct ones on a 1Q chip, and they're the fields users click); a pointer resolving to nothing numeric is recorded `KIND_PTR` and handed back to the scan. **Ordering is rebuilt, not repaired**: an out-of-order arrival writes NOTHING and marks dirty, the next read rebuilds (1.2–5.4 s — cheap enough that there is no incremental repair algorithm to get wrong). **A rebuild MERGES** — rows for pruned snapshots survive and replaying them in ts order is what stops the oldest survivor claiming all 8,000 leaves just changed (the one place data can be lost; three tests). `field_history` gains tier 0 BELOW the curated index (which keeps its tier). Surface: `/param-history/changes` (a `Trends | Changes` tab strip) paged by **snapshot not row** — a regenerate rewrites thousands at once (2,716 measured) and a row-paged feed would hide every other event — each group showing its true count + first 25 rows + "Show all N"; rows read old→new through the docs/76 Δ; `/param-history/param-search` is the typeahead over 11k paths. Verified on real stores: replaying every change point reproduces each chip's newest `state.json` EXACTLY (0 missing/extra/wrong over 4 chips), and incremental ingest == full rebuild on 500 sampled paths/chip. ### Autofit (one-button automatic fitting scheduler)

**Autofit** (`/autofit`; sidebar label **"Auto Calibrate"** since r15/docs/69 — routes/page tokens keep the autofit names) is the closed calibration loop: one button runs a plan of nodes over chosen targets, gates every fit, LLM-audits the residual suspects, **reverts** rejected node writes deterministically, **re-measures** with adapted parameters, and reports everything from an append-only ledger. Doctrine (docs/47, binding): the LLM **never emits a number** — the schema is `{verdict, failure_mode, reason}`; corrections are ①deterministic gates ②revert via `patches[].old` (CAS'd, `coerce=False`) ③re-run with family-keyed parameter adaptations; the calibration numbers always come from the node's own fitter. `core/autofit/`: `families.py` (code-curated registry: metric bands, plausibility + jump limits vs the **pre-update** anchor, feature x-checks — argmax only where provably valid, spectral signal-presence for oscillation/decay/2-D, FIT_TARGET_MAP paths reused + parity-pinned; iq_blobs is **verify-only**, its iw_angle sign convention is node-version-dependent), `gates.py` (G1 node outcome → G4 physical bands → G3 raw-data x-check → G2 metrics/consistency/error-ratios → G5 history; deterministic fail can never be overridden by an LLM accept), `auditor.py` (providers anthropic/openai-compat/fake/off, per-plan call budget, numeric emissions discarded+flagged), `engine.py` (per-target decisions keep/applied/retry/defer, hard-criticality halts only that target's chain, autonomy `full` = apply-with-revert-guarantee + pre-plan pinned snapshot / `review` = restore-at-end), `writer.py` (the ONLY write path: build lock → `batch_set` → `saver.save` → `apply_to_live` with one pull+re-stage retry; reverts are compare-and-swap and only `replace`-op patches), `synth.py` + `simbackend.py` (ground-truth sim chip + corruption modes `wrong_peak/no_signal/noisy/out_of_band/drift`; run folders indistinguishable to every SM reader — the CI accuracy ledger in `tests/test_autofit_gates.py` pins per-family false-accept coverage incl. documented blind spots), `realbackend.py` (drives the Scheduler chassis; lost-wakeup watchdog, heartbeat feeding, engine-owned synchronous ingest with normalized-prefix + time-window attribution). While a plan runs, the scheduler edit-lock **and** every `/scheduler/*` control route 409 (two-masters closure). Presets pin **family keys** resolved against the scanned library at plan build (per-lab renumbering survives). The sim backend is a first-class demo: `/autofit/start {backend: sim}` runs the whole loop hardware-free through the REAL write path. See `docs/56_autofit_scheduler.md` (incl. §7b — the adversarial design-review amendments that shaped all of the above).

**Runner + AI calibration agent (docs/78 — IN PROGRESS, read §17 first).** The programme that turns Autofit into the one-button bring-up loop: *press → experiments run → fits gated → state updated → done when the gates PASS **and** a vision judge accepts the signature* (§1.3). Scope = the 9 families of the x180 chain (03 · 05 · 06 · 07 · 08 · 08b · 09 · 10 · 11). **Shipped: P0–P8 + §17 B3. Open: P3c/P3d (the signature calibration — needs an API key for the shipped provider path) and P9 (needs hardware).** Doctrine amendment (D-1): not "the AI may not emit numbers" but *a number the AI emitted never reaches state.json before passing a tier-A (the node's own analysis, replayed) or tier-B (grid-exact) verifier*. A verification context is the triple **(env × analysis-tree revision × run generation)** — `core/autofit/envmatrix.py` classifies it and `sourceroot.py` materializes a pinned git revision read-only (`git archive`, never a checkout), because no single env replays the whole corpus and the customer tree keeps moving. `corpus.py` derives per-family parameter ranges; `figure_gen.py` + `generator/run_figure_gen.py` regenerate a run's figure through the LAB's own plotting module, with a wrong-fit injection seam (that is what makes a false-accept test set buildable). **Every band in `families.py` is corpus-derived, never invented** — replay real runs, split by the node's OWN accept/reject verdict, keep a floor only if it sits below the accepted minimum and still separates; the ledger is 0 false rejects over 276 accepted / 115 rejected targets, and that method overturned 16 shipped false-rejecting gates (docs/78 §15.2, §15.2b). Update targets are **run-derived** (D-14): flux-point routing (node 06 ASSIGNS the joint offset where 09 INCREMENTS it), `{operation}` filled from the run's parameters and then followed through the chip's alias pointer (`operations.x180 = "#./x180_DragCosine"` — the run names the alias, the node writes the target), π/2 = π/2 under `update_x90`. The vision judge's family knowledge is **versioned data** (`judge_pack.py` + `judge_packs/v1/*.json`, authored from real archived figures): shape and relative geometry only — **Clause B is enforced at load**, violating strings are dropped and logged, because an exemplar that sizes a feature against the swept window teaches the next chip a falsehood. `auditor.py` carries four number-free asks — `judge` (trust), `signature` (the terminator), `compare` (`better|worse|same`, the no-progress stop) and `triage` — with one shared numeric-emission guard and safe defaults (an unavailable judge answers `unclear`/`same`/`unreadable`, never `clear`). **The loop closes (§19):** a target is done only when the gates pass AND the judge signs off on **its own panel**; with no judge configured it finishes on the gates alone and is STAMPED `vision=unavailable`, so no report can imply a check that never happened. Looking is two-stage (§18): ONE `triage` call over the multi-panel sheet asking *which* panels want a closer look, then a dedicated per-target look for the **union** of (gates flagged) ∪ (triage flagged) — union because the two fail differently, and a naive per-target judge would blow the 40-call plan budget on a 17-qubit chip. Also shipped: `action_space.py` (D-3 A/B/frozen/reserved — **`load_data_id` is blocked on the agent path**, bounds data-derived and never from schema defaults, out-of-bound proposals rejected not clamped), `stoploss.py` (three tiers; the plan step cap + wall clock that were absent since the plan was written; tier 2 needs BOTH the metric trend and the vision comparison flat, which is the only thing that catches oscillation), `consistency.py` (the cross-run review — the pair that is each internally consistent and mutually impossible; what to compare is corpus-derived and curated, and the tolerance is a scale the runs themselves report, never a constant), `notify.py` (four events, best-effort) and `replay_score.py` (offline scoring whose metric is *fewer runs to the same conclusion*, never agreement with the operator). **Every verdict carries the context it is only valid inside** (`verification.py`, docs/78 §21.1): `lab_replay` is identified by (env, lib_versions, root + revision, `gate_hash`), `sm_gates` by `analysis_rev` — a content hash of `families.py` + `gates.py`, because no interpreter is spawned for the deterministic gates and naming one would be a fiction. The consumer is `consistency.reconcile`, the only code that reasons across runs: values obtained under different contexts are NOT compared and the refusal is recorded, since a disagreement between two gate revisions is a category error, not physics. `power_rabi`'s `verify_wide` is a **mode switch, not a scaled span** (§21.2) — 230 runs show the family is two experiments (1-pulse survey over `[0.001, 1.99]` vs 20–160 pulses over a median width of 0.3), so widening the narrow window would alias rather than survey.

### FSP → Amplitude Compensation (r12 — never silent)

Editing a port's `full_scale_power_dbm` keeps pulse powers constant only if the amplitudes rescale (`P = FSP + 20·log10|amp|` ⇒ `amp' = amp·10^((ΔFSP↓)/20)` — the identity `autofit/power_rows` pins bit-exact). **Hard contract: amps are never updated quietly and the FSP edit never commits before the user saw the offer** — `/field/edit`(+`-batch`) 409 with `mw_fem.fsp_compensation_plan` (reverse-pointer 2-hop port→wiring→channel traversal, MW outputs only, alias ops skipped, pointer amps disclosed, per-row + top-level DAC-clip warnings on `|amp'|>1.0`) unless `fsp_ack=comp|solo`; the shared `_openFspPopup` lists every old→new and only an explicit choice commits (`comp` = FSP+amps in ONE gid = one Review bundle = one Ctrl+Z). Wired in Explorer/bulk/pair/All-values and the plot-apply popup (per-row + Apply All — comp switches the single edit to one `/field/edit-batch`, acks accumulate across chained 409s); un-wired callers get the honest 409 error string. The conservative identity-confirm banner ("This chip appears to be 'X' — is this correct?", snapshot-remembered via `HistoryManager.remembered_identity`, Yes = stage via `/chip-name/set`, No = `token::identity` memo → fill-in prompt with Browse) shares the same never-automatic doctrine. Pinned by `tests/test_fsp_compensation.py` + `TestIdentityConfirm`.

### Dataset Support

**Multiple windows on one machine (docs/80).** Two ports on one PC works, and separate projects were verified isolated (per-path working copies, per-chip history, WAL'd index) — but the **instance dir is shared**, so `core/instances.py` is the registry of live SM processes: `instance/instances/<pid>.json`, **one file per process** (a shared document would need a cross-process read-modify-write — the very lost-update pattern being closed), liveness by **PID probe not heartbeat** (no new poller; `pid_alive` lives here with `scheduler._pid_alive` as an alias so reconciler and registry can't disagree). Written from existing choke points: `create_app`, the first request (the port is chosen outside `create_app`), both `_activate_quam` branches, `atexit` + window-close. Every write best-effort — bookkeeping never stops the app. **Run ownership**: the queue is a file but `is_running` is in-memory, so a second process couldn't tell a live sibling from a crashed worker — reproduced: window 2's *poll alone* flipped window 1's live run to idle + its item to failed, Start spawned a **second worker on one OPX**, and merely *closing* window 2 wrote "cancelled" over window 1's run. `run.owner_pid`/`owner_port` (claimed by `start`, released at every terminal transition) make it recordable: with a **live foreign owner** `_reconcile_orphaned` and `cancel` touch nothing and `start` raises `ForeignRunnerError` → 409 `scheduler_foreign_owner`; **no/dead owner keeps today's behaviour byte-identically** (that's the load-bearing row — crash recovery is what the mechanism was for). Start is the ONE refusal, because no warning makes two workers on one OPX safe. **Warnings**: only the **same state path** in two live windows raises `_multi_instance_banner.html` (`GET /instances/banner` → `#multi-instance-slot`, refreshed off existing events, dismissal view-only since which windows are open is a live fact). A shared **data folder is deliberately not a conflict** — one chip / two experiment lines is a real workflow and its only loss was fixed at the source. No cross-process file lock (it would trap a user behind a crashed window). **Two chips at once (Part 4)**: runner state is keyed by chip — `instance/scheduler/<chip>-<fs_key hash>/{scheduler.json, scheduler_queue.json, scheduler_logs/}` (readable prefix from `history.chip_name_for`, since every chip folder is literally named `quam_state`). Scoping by the OPEN chip is the only non-circular choice — the runner's own `quam_state_path` lives INSIDE the scoped file. **Settings split** is what keeps this a feature not a chore: `env_python`/`calibrations_folder`/`default_timeout_s`/`continue_without_ui` are machine facts shared at `scheduler/_shared.json`; everything else is per-chip, above all `quam_state_path` (which the worker re-reads per item — a shared copy is how window 2 redirected window 1's run). `routes._sched_inst()` is THE resolver and every scheduler/autofit route already went through it; deliberately NOT scoped: the two `node_scan`/`scan_params` caches (keyed env+folder, chip-agnostic), the autofit **sim world** (throwaway synthetic chip; the autofit *ledger* IS per-chip), queue **presets** (a recipe, not a device fact — they sit beside the scopes), and the **UI heartbeat** (`touch_ui` feeds EVERY local runner: it means "a browser is alive" for closed-tab detection, so scope-keying it would make merely SWITCHING chips pause the run you navigated away from). Window close cancels via `cancel_all_local()` (own runner registry, not a directory). `migrate_legacy_scope` runs once at startup (flag-gated) into the scope named by the legacy `quam_state_path`, else `_nochip` — copy → **verify** (same item ids + settings read back) → delete the originals; unverifiable keeps both. **Post-implementation audit fixed three**: the LLM auditor's settings (provider/model/**API key**) had become per-chip so the user's `instance/autofit_ai.json` stopped being found and the audit silently turned itself off (now instance-level); an unfixable run (`node.json` holding a list, permission error) re-parsed FOREVER and its `_incomplete_paths` membership defeated the B27 date-dir skip so every SIBLING re-parsed too — bounded by `_INCOMPLETE_MAX_TRIES=3` identical-fingerprint failures (a real writer moves the fingerprint, so mid-write is never cut short; a later repair re-parses normally); and the `partial` catch-up was unbounded, turning a 60s poll into 1.2s on a workspace that always exceeds the budget (`POLL_MAX_CATCHUPS=5`). Pinned by `tests/test_multi_instance.py` (ownership matrix vs a REAL spawned live process) + `tests/test_scheduler_scope.py`.

**Polling under a concurrent writer (docs/80).** A data folder is written by something that is not us — a qualibrate node mid-run, or a **second State Manager window** (two ports on one machine is supported; separate projects were verified to stay isolated — per-path working copies, per-chip history, WAL'd index). That writer isn't atomic at the folder level, so the newest run is normally mid-creation, and three things used to turn that into failure. ① Scan reads go through **`safe_io.scan_json`** (one attempt, no sleep, no exception) instead of `read_json`, whose 4-attempt/0.9 s ladder is right for a live `state.json` and pure latency for a run that simply isn't finished (`read_json(attempts=)` exists for the same reason; the live paths keep the ladder). ② A file present-but-unreadable sets `RunInfo.incomplete` → sentinel `_INCOMPLETE_FP` + membership in `_incomplete_paths`, which forces re-parse **and** defeats the B27 date-dir short-circuit (writing inside a run folder moves that folder's mtime, not its date dir's) — without it a completed run could freeze with partial metadata; the row is still published, since id/name/date/time come from the folder name. ③ `/datasets/changes-since` isolates each folder (a raiser used to 500 the whole poll — invisible to the user, permanently frozen table), holds a failed/skipped folder's cursor at `ts` like the D8 path, has a wall-clock budget (`_POLL_BUDGET_S`) reported as `partial`/`skipped`, and can only return 200; the client aborts at 10 s, clears the in-flight latch in a real finally (a never-settling request used to wedge polling until reload), backs off on failure, treats non-2xx/malformed as failure (never a cursor advance), and catches up promptly on `partial`. `_save_tags(touched)` **merges over the on-disk file** — `quashboard_tags.json` is the one thing SM writes inside a data folder and sharing one is legitimate (same chip, two experiment lines), so the conflict unit is one run, not the whole file. **A shot index is not an axis (docs/82).** `_default_view` ordered sweeps by SIZE, and a repetition axis is always the biggest dim in the file — so a `readout_power_optimization` run plotted I against `n_runs`=2000 instead of `amp_prefactor`=10 (RB: `average`=100 on x, the decay's `circuit_depth` on y). Averaging is what makes the default view of a single-shot node match every other node's: only a handful of ~50 node types save a shot axis at all (the single-shot nodes + two-qubit RB), the rest average it on the OPX. It is **kept** when there is nothing else (iq_blobs' `Ig(qubit, n_runs)` IS the per-shot scatter; of 502 such real cubes none had another plottable dim) — and a short sweep diverted to the overlay bucket is reclaimed for x before a shot axis is. Never silent: the controls strip renders `averaged over n_runs (2,000 shots)`. Ripples: the reduced dim leaves `dims` (the client flattens against exactly those sizes), the decimation gate takes `shot` too (a kept 6,000-shot axis must still decimate), and the IQ partner read inside that branch is averaged over the SAME axes or |IQ| silently disappears. **Inline-commit stability (docs/75).** One field commit still re-renders the whole `#inspector-pane`, and that swap REMOVES the focused input — which fires `focusout` on it with the typed value still in place. The Tab/click-away commit handler must therefore never fire on a form whose commit is in flight (`InlineCommit.inFlight` = htmx's `.htmx-request` **or** our `data-committing` marker from `htmx:beforeRequest`/`afterRequest`): the duplicate is dropped by htmx's default `hx-sync`, and a *dropped* request means htmx never called `preventDefault()`, so the browser performed the form's NATIVE submission — a full-page GET carrying `?path=…&value=…` (the "Leave site?" prompt, or a silent reload with nothing pending). Armor: a document-level bubble-phase `submit` listener `preventDefault()`s every form carrying `hx-post`/`hx-get` (skipped when htmx is absent, so plain-HTML fallback survives). `window.InlineCommit` then restores focus/caret/panel-scroll across the re-render — `key` mode (Enter → same field, matched by `dot_path`/`data-param`, never DOM index), `index` mode (Tab → the n-th focusable of the rebuilt pane), `none` (focus left the pane); it only ever fills focus the swap DROPPED (`activeElement === body`), a click/tap CANCELS the pending restore (so commit→open-another-pulse can't drop focus into the new pulse's same-named field), and a wheel/PageUp abandons the scroll restore. Post-commit refreshes are **debounced, not removed** (`pulses-changed delay:400ms`, `diagnostics-changed delay:500ms`). Pinned by `tests/pulses_commit_selfcheck.cjs` + `tests/test_pulses_commit.py`.

### Generate Config + Config Viewer

`core/config_generator.py` drives the **Generate Config** wizard: discovers conda envs, probes for the QM stack (`qualang_tools`, `quam_builder`, `quam`), spawns `generator/run_build.py` in a user-selected env, and reads the resulting `_result.json`. The State Manager process never imports the heavy QM libraries. `generator/run_build.py` + `generator/run_generate_config.py` are standalone scripts run by the chosen interpreter (shared stdlib-only helpers live in `generator/_script_common.py`, imported after a defensive `sys.path` insert). Both runners share `_run_script_outcome()`; the wizard's build-result step has a **Preview config** button (`POST /generate/preview-config`) whose result is stashed and transplanted onto the store by `/generate/load` when the content hash matches (seed-on-load).

After `machine.save()`, the build flow runs a post-save fix-up that rewrites each readout MW input port's `downconverter_frequency` as a JSON pointer to its paired MW output port's `upconverter_frequency` (`_link_input_downconverters_to_outputs` in `generator/run_build.py`). Hardware-wise these always share one physical LO; encoding the input as a pointer locks the constraint so it can't drift under later edits. Matches the example-9q-rack encoding already in production.

The Populate step is **absolute-first**: RF frequencies are the primary input, with the LO auto-derived per MW-FEM port pair by `solveLoWindow` (`generate.js`) — minimize max|IF| subject to the ±400 MHz IF window, a Nyquist band covering every member under `bandOf`'s band-1-first precedence, and the 5 MHz resonator demod hole (xy may sit at IF=0); named warnings + midpoint fallback on infeasibility. A **Power input** toggle (`quam_gen_power_mode`) adds an absolute-dBm mode: pulse powers typed in dBm, the port `full_scale_power_dbm` auto-allocated (strongest pulse picks the integer FSP `ceil(P+6.02)`, preferred [0,10], floored at 0 / capped at 18, amp band 0.01–0.5; readout is a bank edit — one dBm per feedline under an `n·amp ≤ 0.5` coherent-sum budget). Stored spec representation is identical in both modes (fsp + amps; `P = FSP + 20·log10(amp)` is lossless), so `run_build.py`, `validate_spec` and old drafts are untouched. The Σ|amp| > 1 feedline clip warning is **mode-independent** (a DAC physical fact — it fires in manual mode too); the 0.5-headroom advisory and per-tone findings stay absolute-only. Pinned by `tests/generate_power_selfcheck.cjs` (user example: saturation −20 dBm → FSP 0 / amp 0.1).

The r3 feedback batch (see `docs/53_generate_feedback_r3.md`) added: **as-you-type inline validation** in the Populate step (debounced per-cell `validateCellValue` — hardware-reach/band/window/demod-hole/amp/feedline-Σ/FSP checks, unit-aware, red/amber cell decoration; JS↔Py constants parity pinned against `diagnostics`/`spec_constraints`); **CZ automatic control/target orientation** (higher-RF_freq qubit = control; `czAutoOrient` flips the stored pair + its whole identity web on every frequency commit, `cz_order: manual` pins, CR/regenerate never flip, `run_build._cz_order_warning` is the build-time safety net); **user-settable qubit naming** (step-4 scheme presets `q1…`/`q0…`/grid-letters/custom + per-qubit rename via one-pass `applyQubitIdMap`; name rule `^q[A-Za-z0-9_]+$` mirrored in `validate_spec`); a **default-value presets archive** (`core/gen_presets.py`, `instance/gen_presets/`, `/generate/presets` routes, capture uniform→defaults / differing→overrides, apply fill-only-empty or overwrite); and **editable Python build-script export** (`core/script_emitter.py` — step-7 toggle writes `01_make_wiring.py`/`02_build_machine.py`/`03_generate_config.py`/`README.md` with values inlined; fidelity = build_connectivity insertion-order mirroring + machinery extracted verbatim from `run_build.py` via `inspect.getsource`; end-to-end JSON-equality pinned by `test_script_emitter_live.py`).

**QDAC-II bias (docs/119).** Some labs flux-bias specific qubits from an external QDAC-II DC source instead of an OPX LF-FEM port — there's no upstream qualang_tools/quam_builder support for this, only the customer's own `quam_config.qdac_components` (`QdacInstrument`/`QdacBiasLine`/`QdacBiasedFixedFrequencyTransmon`), imported directly when present. Everything is DEGRADE-only (two new `capabilities.REGISTRY` ids, `instr.qdac` + `wire.qdac_trigger_line`, requested only when `spec.qdac.qubits` is non-empty): a missing module, a failed trigger allocation, or a per-qubit attach error leaves that qubit with no z/bias component and a warning, never a crash. The trigger wiring is a **second, isolated `Connectivity`** (sharing `instruments` for a conflict-free port pool) because `create_wiring`/`build_quam` raise on any wiring line type they don't recognize and the QDAC trigger's custom `"qt"` type isn't in their whitelist — confirmed against the customer's own forked wiring builder. `_apply_qdac` reassigns the qubit's runtime `__class__` **in place** (same object identity, same already-built children) since `QdacBiasedFixedFrequencyTransmon` differs from the qubit's built class only in the type of `z`; must run before `apply_populate`/`_finalize_pair_gates`, whose guards now check `hasattr(z, "independent_offset")` / `hasattr(moving_q.z, "operations")` instead of bare `z is not None` (a QDAC-biased qubit's `z` has neither). The top-level `state["qdac"]` instrument entry and the `wiring.qubits.<qid>.qt.digital_output` pointer are both **post-save file patches** (atomic tmp+`os.replace`, same pattern as `_link_input_downconverters_to_outputs`) — `machine.qdac = ...` is silently dropped by `Quam.save()` since the QPU root classes declare no such dataclass field, and `machine.wiring`'s `setdefault` returns detached copies. Wizard UI is TWPA-style (step 4 band, no resource-pool/topology-diagram integration); `deriveLines()` omits a QDAC-biased qubit's flux line, `validate_spec` refuses a qubit being both QDAC-biased and OPX-flux-wired. Verified end-to-end on a real 20-qubit chip via conda env `CQT_20Q` (quam 0.6.0/quam_builder 0.4.0/qualang_tools 0.23.0 + the customer's editable-installed `quam_config`) — `tests/test_generate_qdac_live_build.py` builds a mixed QDAC+flux-tunable spec and asserts every QDAC key lands with zero degrade warnings. Pinned by `tests/test_capabilities.py`, `tests/test_config_generator.py::TestValidateSpecQdac`, `tests/test_generate_qdac.py` (wizard JS selfcheck), and the regenerated `tests/golden/scripts_bundle_cz/02_build_machine.py`.

`core/config_view.py` is the **Config Viewer**: shows the QM config dict and per-pulse waveform plots that a calibration script would receive after `machine.generate_config()`. Same subprocess pattern as the wizard. In the sidebar it nests under Generate Config as a collapsed-by-default sub-item (`#config-subnav`); the per-qubit/pair detail sections carry inline Regenerate buttons. `waveform_for_operation()` returns `{element, operation, pulse, traces:[...]}` (I+Q both; `length_inferred` flags the 16-sample placeholder). The cache is staleness-checked at render time: `meta["basis_hash"]` (hash of the working-copy files at regenerate) vs `working_copy.content_hash(store.state, store.wiring)` — see `_config_stale()` in `web/routes.py`. See `docs/27_config_generator.md` and `docs/30_config_viewer.md`.

### Re-generate Config

**Re-generate config** (sidebar, nested under Generate Config; `/regenerate`) lets a user take a chip they already built, **edit its structure** in the wizard (move ports, change bands, add/remove qubits or pairs, gate family), rebuild it fresh, and **keep every calibrated value** — plus walk away with a single editable **Python build recipe**. Pipeline (`core/regenerate.py`): `regen_spec.reconstruct_spec` inverts the chip → spec (wiring pinned from port pointers, pairs from `state.qubit_pairs`, populate by inverting `apply_populate` through pointer chains) → user edits in the wizard (`mode="regenerate"`) → `config_generator.run_generator` builds fresh structure into a NEW folder (never the source) → `regen_merge.merge_states` carries calibrated values (tier-1) + grafts user-added op/macro subtrees (tier-2) → `regen_script.emit_build_script` writes `build_<chip>.py`. The State Manager process never imports quam/quam_builder; everything here is pure JSON/string work + the subprocess build.

Merge fidelity details: **entity collections** (`qubits`/`qubit_pairs`/`ports`/`octaves`/`mixers`) are never resurrected. **TWPAs build natively** — modern `quam_builder` exposes `Connectivity.add_twpa_lines`, so `reconstruct_spec` pins each pump line from `wiring.twpas`, `run_build` builds them, and the merge carries the OLD pump calibration via tier-1 (LabA: 4 TWPAs, 71 config elements). Only the legacy 0.2.0 builder (no TWPA wiring registry) can't; there `graft_twpa_wiring` carries the OLD `twpas` + `wiring.twpas` + referenced ports as a fallback so the chip still compiles. **Pair ids** are reconciled by `(control, target)` membership (builder may emit `qA2-A1` vs source `qA2-qA1`) — at merge AND at the build-time `populate.pairs` seed lookup (`run_build._match_populate_pairs`, 3-tier: exact/spelling/membership); reconstruct keys per-pair populate by the canonical control-target id and the wizard re-keys instead of deleting (2026-08-02 ② amendment). Redundant OLD ops the rebuild re-expressed under new names (unreferenced + broken pointers) are **pruned**. **Cross-generation schema gate** (2026-08-02): `run_build` harvests the build env's dataclass field schemas for every `__class__` in the fresh state (`_result.json["class_schemas"]`), and tier-2 refuses to graft an OLD-only key into a `__class__`-tagged dict whose class doesn't know that field — old-stack renames/removals (e.g. `CZGate.duration_control` → `duration_qubit` in quam_builder 0.4.0) are `Quam.load()` killers, dropped VISIBLY as `schema_dropped`; plain-container keys (`operations`/`macros`/`extras`) still graft, no-schema/unknown-class falls back to legacy graft, and `__package_versions__` is always the NEW build's (never carried/grafted). **Adaptive reconstruction + populate-protect (r16, docs/72)**: `reconstruct_spec` unions the declared `ports` inventory into the FEM set (a slot whose only channel was user-trimmed/nulled no longer vanishes — the LabD-17Q slot-7 report), derives qubits wiring∪state, tolerates explicit-null channels, and assembles controllers after the wiring-only-pairs recovery; the merge accepts `protect_paths` — the fanout of the user's in-wizard Populate edits (`core/regen_populate.py`; baseline = the hydration-time populate shipped back by the client) — so wizard edits are never reverted by tier-1 (the one exception: a hand-tuned z delay under a band-crossing edit is kept + reported). `applyLoAssignments` is fill-only-empty in regen (explicit "Re-solve LOs" opts in), `autoApplyStandardDefaults` no-ops there, populate gains a user-settable `band` column (overlapping Nyquist bands — `_set_channel_lo` honors the override, z delay follows), scripts export defaults ON with the path following `<output>\state_gen_scripts` until touched, and `/regenerate/build` honors `scripts_dir`. Transparency counters (`carried`/`grafted`/`superseded`/`residual_lost`/`pruned_ops`/`twpa_wiring_carried`/`dangling_grafts`/`schema_dropped`/`populate_protected`/`populate_conflicts`) surface in the build-result panel. An exact-spec **sidecar** at `<out>/.regen/generate_spec.json` (hash-keyed, subfolder so `Quam.load()` ignores it) is preferred on a later re-generate. **A pair reference is a POINTER, and it can be TWO hops (docs/118).** `regen_spec` and `regen_merge` read a pair's control/target with `str(ref).split("/")[-1]`, right only for a one-hop `#/qubits/qX` — a modern quam_builder chip stores `#/wiring/qubit_pairs/<p>/c/control_qubit` -> `#/qubits/qX`, so the split returned the literal `control_qubit`. Every pair was dropped from the reconstructed spec with a FALSE "references qubit(s) not on this chip" note, `populate.pairs` came back empty, pair-id reconciliation matched nothing — and the build still reported SUCCESS while losing 59% of the pairs' calibration (1,878 -> 774 leaves on a real 10Q chip). `qubit_ref_name(root, ref)` walks the chain ONE HOP AT A TIME (the module's `_resolve_ptr` follows the whole chain and returns the qubit DICT, which cannot name the qubit) and takes the last segment of the FINAL pointer, so a one-hop chip is byte-unchanged; `merge_states` gained `old_wiring`/`new_wiring` because a `#/wiring/...` reference only resolves inside the state it came from. After: 9/9 pairs, all nine CZ macro variants kept, residual_lost 200 -> 0, **98%** of pair leaves carried, output `Quam.load()`s. Also fixed: the transparency lists ship `[:200]` and the panel counted the ARRAY, so a rebuild that lost 1,104 leaves displayed "200" — `*_total` counts now ride alongside and the panel prefers them. Pinned by `tests/test_regen_pair_pointers.py`. The emitted **recipe** combines QM's generate + populate into one file (public idiom only: `qualang_tools.wirer` + `quam_builder` + `quam_config.Quam` + `pair_gates`), pins ports, seeds real bands (never hardcoded), and branches fixed vs tunable coupler at runtime — verified building both chip classes end-to-end in the LabB env. It's a *recipe* (structure + design-time seeds), not a calibration snapshot. See `docs/51_regenerate_config.md`.

### Environment Capability Validation

A build only works if the selected conda/venv env exposes the exact functions the chip needs, and **package versions lie** (LabB ships `quam_builder 0.2.0` yet has `add_twpa_lines`). So we detect by introspection and tell the user — before building — what this env can/can't make. `generator/probe_capabilities.py` runs in the env (stdlib-only at import; a module-level `CATALOG` of `{id: locator}`, no QM imports at load) and `detect()` emits `{id: {available, detail}}` via `import + hasattr`; `run_build.py` imports `CATALOG_IDS` from it so detector and consumer can't drift. `core/capabilities.py` (SM side) owns `REGISTRY` (label/package/symbol/**produces**/**fix**/severity), `required_capabilities(spec)` (pure; context by *inclusion* — e.g. `pair.fixed_pair` only under `cz_fixed`), and `assess(spec, manifest) → {buildable, ok, blockers, warnings, inventory}`. `config_generator.probe_capabilities()` runs the deep probe for the *selected* env with a **version-keyed** cache (the older probe cache keys on interpreter mtime — stale after a `pip install`; not inherited). Three buckets: **blocker** (build would fail → hard-block), **degrade** (build succeeds, feature dropped/falls back → soft-block behind `ack_degrades`), available. `/generate/build` + `/regenerate/build` enforce server-side, independent of the stray-JSON `force` (one ack never collapses two gates). UI: report card in `enterReviewStep` + "Re-check environment". The `REGISTRY` id set is pinned equal to `CATALOG_IDS` by a test. Pulse-class locators are **multi-home** (`_PULSE_HOMES`: quam → quam_builder arch → quam_builder common — quam 0.6.0/quam_builder 0.4.0 moved SNZ/Erf/GaussianFiltered* out of `quam.components.pulses`); the same home list lives in `run_build._pulse_class` and `run_waveform_golden`, pinned in sync by `TestPulseHomesInSync`. See `docs/52_env_capabilities.md` + `docs/53_qop37_alignment.md`.

### Type Coercion Philosophy

`modifier.py` casts new values to the original field's type but **never validates ranges**. Real QUAM data has coupler amplitudes >1, negative T2, angles outside [-π, π] — trust researcher input.

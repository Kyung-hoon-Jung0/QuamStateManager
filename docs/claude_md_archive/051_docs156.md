**The Calculator as its own browser window (docs/156, 2026-09-03 — user feedback: "SM 창 내부에서만 floating함").** Browser mode only, user-scoped. The popover header's ↗ (`.calc-popout` → `openCalcWindow`) opens `GET /calc-window` via a SIZED `window.open` under one window name (`quam-calc`) — a real OS window, movable across monitors, outliving every navigation of the page. `/calc-window` is a standalone document (`calc_window.html`: no shell, no htmx/app.js, exactly one script, and NEVER `_ctx()` — the calculator is chip-independent and must be inert beside a chip); the sections are ONE partial (`_calc_body.html`) both surfaces render, and the theme boot is ONE partial (`_theme_boot.html`) both documents include. While the window lives, ↗ / the Calculator button / Alt+C FOCUS it instead of opening a second calculator in-page; the popover closes when the calculator moves out and returns once the window is closed. The standalone document (`#calc-popover.calc-standalone`) computes on load, focuses the first field, has no drag/anchor/outside-click closer, closes the WINDOW on Escape, and remembers size + screen position in `quam_calc_win`. **Desktop shell is gated**: under pywebview the WebView2 backend answers `window.open` by navigating the SAME window (`edgechromium.py on_new_window_request`), so calc.js checks `window.pywebview` at click time (injected after navigation completes — a load-time check is unreliable) and hides the ↗ on `pywebviewready`; a true second native window needs a `js_api` bridge the app does not have (docs/156 §4). Known residual: the reference lives in the page, so a FULL reload loses it and the popover reopens in-page while the window still exists. Pinned by `tests/test_calc_window.py` + `calc_window_selfcheck.cjs` (35 asserts, 8/8 mutations); CDP-verified in real headless Chrome.

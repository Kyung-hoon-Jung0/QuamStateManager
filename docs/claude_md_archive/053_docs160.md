**Ctrl+Z after Apply-to-live writes the chip (docs/160, 2026-09-03 — customer, CRITICAL: "apply to chip을 적용한 이후에도 ctrl z가 되기를"). Covenant amendment #3 (docs/107 → 117 → 120 → 160):** a direct live write happens on an explicit Apply press, inside an armed Auto-Sync session, OR as the undo/redo of a change that reached the chip through one of those — the Apply press was the consent, Ctrl+Z withdraws it. Machine-wide setting `instance/undo_live.json` (default ON; Settings → "Ctrl+Z writes live"; `POST /settings/undo-live`; OFF = docs/107 stage-only byte-for-byte). **A**: `_undo_journal_step` stages the inverse then `_undo_live_flush` pushes it through the ONE door (`_sync_pull_apply_to_live(journal=False)` — a walk step is recorded by the CURSOR, never as a unit); the cursor is persisted (sidecar v2 `"cursor"`, `undo_journal.load_state/save_cursor`); Ctrl+Shift+Z re-applies forward via `_redo_journal_forward` (CAS on the unit's OLD values, un-staged on refusal; a `jrn_live` redo frame, with a journal-forward fallback when the RAM stack is empty after a restart); `append_units` truncates past the persisted cursor (a new action discards the redo branch — a staged-only step never moves that cursor, so OFF mode is unchanged). Refuses and STAGES with the reason in the toast + the Undo trail tier: setting OFF · the working copy not provably at the sync point (`_working_at_sync_point`: tray edits, a staged snapshot, saved-but-unapplied content — the door pushes the WHOLE working copy) · journal drift · archive · a live foreign window; and ROLLS BACK all-or-nothing when the door refuses (the staleness gate / a write error: `_rollback_walk_step`, cursor restored, "Not undone — take the live changes, then undo again").

**A push that finds the chip moved MERGES, instead of turning itself off (docs/187, 2026-09-12 — customer, on-site).** "live edit에서 enter를 누르면 그 다음부터 auto sync가 깨짐" + "이유없이 pull&apply 문구가 뜬다 (외부변경없는데도)". One mechanism, and not an edge case on their bench: SM (`instances/4928.json`, :5050) has `260907_KRS_5Q` open, that folder is **qualibrate's own `state_path`**, and its log saves the machine there on every node run — every 30–60 s. So a node writes the chip *between two of the user's edits* as a matter of course, `/state/apply-to-live` raises `StaleLiveError`, and docs/117's disarm fired: **Auto-Sync died within a minute of arming, and every later edit silently stopped reaching the chip while the user kept typing** (the conflict tray is also where ⇄ Pull & apply lives, which is symptom 2). **Two reproduction rounds failed first** — three Enters on three rows 4 s apart, then four rapid Enters on ONE row with all three switches on, both landing every edit — because both held constant the one thing that matters: another program writing the chip. The fix: a session that armed **pull** has already granted SM permission to take live changes, and a push that finds live moved is precisely what pull exists to resolve, so that case merges (pull → re-apply the pending edits on top → push) rather than disarming. It is the composition of two permissions the user already granted, `pull_replace`-neutral (that flag governs whether an auto-PULL may DISCARD the user's values; this keeps them), and **push-only sessions plus the legacy `/auto-apply/arm` door keep docs/117's disarm byte for byte**. The decision is the server's (docs/120 item 8); the client only presses `doStateSync('apply')` — after waiting for the shared `_applyInFlight` latch, because the signal arrives with the flush's own response, BEFORE that flush releases it, and doStateSync bails on a held latch **silently** (bounded ~2 s). A **merge budget of 3 consecutive failures** then disarms after all; an apply that lands refills it. Measured before/after in real Chrome on a copy of that chip with an outside writer doing what `machine.save()` does: `auto=null` + conflict + the edit never landing → `auto=1`, no conflict, **the outside write survived AND the user's edit landed**. **(3) The conflict tray showed no session at all** — both `pillOn=false` AND `pillOff=false` in every pre-fix snapshot, because that tray REPLACES `#pending-tray` where the pill lived: nothing said whether Auto-Sync was on, nothing said it had just been turned off, and there was no control to turn it back on. The pill is now ONE partial (`_auto_sync_pill.html`) included by both trays — the extraction proved inert by rendering **eight pill states byte-for-byte identical** — and both conflict sites go through one `_conflict_tray()` helper, since a caller that forgets any of `auto_sync` / the two armable verdicts / `change_count` makes the pill render as *nothing*, silently. The tray also SAYS it: “still on and is resolving this itself” while the merge runs, “has been turned **off** … until you turn it back on with the pill above” when it disarmed, and nothing to a user who never armed it — which needed the verdict decided BEFORE the render (the disarm used to happen after the body was a finished string) and the session popped first (or the pill paints itself ON beside a line saying the opposite). Real Chrome, two worlds: pull+push → `auto=1 pillOn=true`, no conflict, both values on the chip; push-only → `auto=null pillOff=true saysTurnedOff=true`, the edit safe in the working copy. Traps paid: a macro imported by the INCLUDING template is invisible inside an include (`'icon_bolt' is undefined` the moment there was a second caller), and `test_web`'s `TestRound15ChromeHiding` pinned the wrapper's presence in the tray FILE — it follows the include now and pins the rule instead. **(2) A replace-pull that discards your edits now says so.** Found checking whether (1) covered the panel's DEFAULT (all three switches on) — it did not, and this is a second way the same complaint shows up. Measured: `replace=False` → pull 204, the pending edit survives (it asks); `replace=True` → pull 200, **pending 2 → 0, the value reverts**. That is what the checkbox says, and the semantics are unchanged — what was wrong is that the server had always announced it (`autoSyncPulled {"replaced": true}`) and **a grep of the whole tree found NO consumer**: no listener, no template, nothing. On a bench where a node writes every 30–60 s, a value the user had just typed reverted under their cursor with no explanation. The pull now counts what it is about to drop **before** pulling (afterwards there is nothing left to count, and a toast must not understate), and one warning names the number and the way back — which is real, since that pull already snapshots `kind="backup"` exactly when discarding, and a pin asserts the snapshot is taken so the sentence cannot become a lie. **A 25-agent adversarial review round then found 18 defects in this fix, 13 surviving refutation (docs/187 §review)** — every one in the fix itself, and the two that mattered most were reviewers asking the sharp version of my own claims. **R1** (raised 3× independently, measured): a landed MERGE never refilled the budget, because `merge_tries` was cleared only in `/state/apply-to-live`'s tail while the merge goes through `/state/sync?mode=apply` — so the budget counted CONFLICTS and the session disarmed after three merges that all LANDED, i.e. the reported bug again three edits later; one `_auto_apply_landed()` helper now runs at both doors. **R2**: the signal named no chip and `/state/sync` has no chip gate — tolerable while a human pressed it, not when the server asks the client to press it ~2s later against a shared context registry;

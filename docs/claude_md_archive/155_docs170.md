**The run table's cold build lands on nobody's click, and the "N new" chip refreshes (docs/170, 2026-09-05).** Two customer reports measured in real Chrome against two builds side by side: the Datasets path's server code was identical, and what was slow was structural — the docs/142 E cold build's *continuation* ran unbounded on the user's first Datasets click (31.6 s at the customer's share latency), three page-load requests each built the same store, and Rescan re-parsed every run then reloaded the whole page (51 requests). Now: `_get_or_create_store` is single-flight per folder and takes a `deadline` (the render passes `_RENDER_SCAN_BUDGET_S` = 3 s and shows an honest *still indexing* note that the delta poll clears; the deadline is checked per RUN and a date dir cut mid-walk gets no fingerprint); `_parse_run_folder` hashes the file bytes and hands back the RunInfo it already holds when nothing changed (Rescan still re-READS every run — docs/105 #5 holds — it just stops re-parsing 2,655 unchanged documents); Rescan swaps the partial on its own date tab instead of `HX-Redirect`. The chip: `sync-badge.js` loaded AFTER `app.js`, so the click handler was never registered — order fixed, registration re-armed after parse, and the click now presses the sidebar ↻ and the Datasets Rescan (`window.refreshRunLists`) instead of opening a card.
